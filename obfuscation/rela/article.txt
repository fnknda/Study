Abusando SHT_RELA para ofuscar código
(Re)descobrindo uma técnica                             ~ Fnknda<joao@fukuda.sh>

---[0x00] INTRODUÇÃO -----------------------------------------------------------

A inspiração inicial para essa técnica veio de um dos artigos mais recentes do
tmp.0ut, o Relocation Revelation[0].

Naquele artigo, é explorado o conceito de relocações em arquivos ELF, falando
sobre as seções `SHT_REL` e `SHT_RELA`, e relacionando com outros conceitos
talvez mais conhecidos como o GOT (Global Offset Table) e o PLT (Procedure
Linkage Table).

O intuito da técnica aqui apresentada é abusar desse mecanismo do formato ELF
para sobrescrever, em tempo de execução, o código armazenado em memória durante
o processo de *linkagem* (antes da execução ser passada para o código em si).

---[0x01] BACKGROUND -----------------------------------------------------------

A ideia de transformar a relocação em ofuscação vem de uma certa predisposição
induzida.

Vários dos artigos nas primeiras edições do tmp.0ut falam sobre ofuscação, desde
EPO (Entry Point Obfuscation)[1][2][3] a polimorfismo[4] e VMs[5], e já que o
hobby de malware começou por lá, o tópico foi um dos primeiros pontos de contato
e, consequentemente, interesse que tive com o formato ELF.

Fora ler artigos, também participo esporadicamente de alguns CTFs (Capture The
Flags), e ofuscação aparece em peso em categorias como engenharia reversa e
exploração de binários.

A ofuscação está em todos os lugares! Não tem como ver uma coisa que muda seu
código dinamicamente e não pensar "vou reescrever meu código inteiro usando isso
aqui."

---[0x02] EXPLORANDO A IDEIA ---------------------------------------------------

O artigo base[0] nos da uma ideia boa de para que serve e como utilizar as
seções ELF `SHT_REL` e `SHT_RELA`, mas não nos passa todos os requisitos que o
ELF precisa cumprir para que a relocação funcione, isso cabe a nós descobrir.

Já que o objetivo é escrever um arquivo ELF simples para implementar essa
técnica antes de nos aprofundarmos mais, seria interessante fazê-lo na mão.

Primeiro, cria-se um executável com o tipo `ET_DYN`, contendo somente o básico
(os códigos-fonte utilizados estão disponíveis no apêndice):

+ +-Elf64_Ehdr------------+
+ |                       |
+ | eh_type = ET_DYN      |
+ | eh_phnum = 1          |
+ |                       |
+ +-Elf64_Phdr[]------[0]-+
+ |                       |
+ | p_type = PT_LOAD      |
+ | p_flags = PF_R | PF_X |
+ | p_offset = code_off   |
+ |                       |
+ +-código----------------+
+ |                       |
+ | nasm -f bin code.s    |
+ |                       |
+ +-----------------------+

Esse arquivo executa o código escrito em `code.s` e nada mais. A partir daqui,
começamos a incrementar o arquivo.

Já que o `SHT_RELA` é uma seção ELF, vamos primeiro analisar a estrutura
`Elf64_Shdr`. Ela tem alguns campos que requer um pouco mais de atenção.

  +-Elf64_Shdr--------------------+
  |                               |
  |    typedef struct {           |
  |      uint32_t   sh_name;      | *
  |      uint32_t   sh_type;      | *
  |      uint64_t   sh_flags;     | *
  |      Elf64_Addr sh_addr;      |
  |      Elf64_Off  sh_off;       |
  |      uint64_t   sh_size;      |
  |      uint32_t   sh_link;      | *
  |      uint32_t   sh_info;      | *
  |      uint64_t   sh_addralign; |
  |      uint64_t   sh_entsize;   |
  |  } Elf64_Shdr;                |
  |                               |
  +-------------------------------+

De inicio, vemos que na *manpage* do ELF (`man elf`) o primeiro elemento do
arranjo de `Elf64_Shdr`s em arquivos executáveis é uma estrutura com todos os
seus campos definidos como zero.

Dentro da estrutura em si, o valor de `sh_name` é um offset que aponta para uma
string da seção da tabela de strings (`SHT_STRTAB`), cujo índice da seção é
definida no campo `e_shstrndx` do `Elf64_Ehdr`.

Outros dois campos interessantes são `sh_link` e `sh_info`. Seus significados
mudam de acordo com o tipo de seção[6]. Para o nosso `SHT_RELA`, `sh_link`
contém o índice na tabela de seções para uma `SHT_DYNSYM` associada (outra
`Elf64_Shdr`), e `sh_info` contém outro índice na tabela de seções, dessa vez da
seção em que esta sendo aplicada as relocações (no nosso caso, um `SHT_PROGBITS`
da seção `.text`).

Em `SHT_DYNSYM`, `sh_link` aponta para a `SHT_STRTAB` associada, e `sh_info`,
contem o valor um maior que o último simbolo local listado na tabela de
símbolos. `SHT_STRTAB` não tem nenhum significado definido para os campos
`sh_link` e `sh_info`.

O campo `sh_flags` também tem valores específicos dependendo do `Elf64_Shdr`[7].

Na estrutura `Elf64_Rela`, em um arquivo executável, o campo `r_offset` contém o
endereço virtual do nosso alvo de relocação, `r_info` tem dois valores em um:
O tipo de relocação (`ELF32_R_TYPE(i)`) vai determinar qual calculo[8] vai ser
utilizado para chegar no valor final que vai ser colocado no endereço apontado
pelo campo anterior, e o símbolo (`ELF32_R_SYM(i)`) é um índice na tabela de
símbolos associada (indicada no campo `sh_link`, em `SHT_RELA`).

  +-Elf64_Rela---------------+
  |                          |
  | typedef struct {         |
  |     Elf64_Addr r_offset; |
  |     uint64_t   r_info;   |
  |     int64_t    r_addend; |
  | } Elf64_Rela;            |
  |                          |
  +--------------------------+

  +-<elf.h>--------------------------------------------------------------------+
  |                                                                            |
  | #define ELF64_R_SYM(i)            ((i) >> 32)                              |
  | #define ELF64_R_TYPE(i)           ((i) & 0xffffffff)                       |
  | #define ELF64_R_INFO(sym, type)   ((((Elf64_Xword) (sym)) << 32) + (type)) |
  |                                                                            |
  +----------------------------------------------------------------------------+

Por ultimo, a estrutura `Elf64_Sym` (elemento da tabela definida pela seção
`SHT_DYNSYM`). Deixo a explicação dessa estrutura para uma outra hora. Para
agora, basta saber que, igual à tabela de seções, essa também começa com um
elemento cujos campos são todos definidos como zero. Isso inclui os campos
`st_value` e `st_size`.

 +-Elf64_Sym-------------------+
 |                             |
 | typedef struct {            |
 |     uint32_t      st_name;  |
 |     unsigned char st_info;  |
 |     unsigned char st_other; |
 |     uint16_t      st_shndx; |
 |     Elf64_Addr    st_value; |
 |     uint64_t      st_size;  |
 | } Elf64_Sym;                |
 |                             |
 +-----------------------------+

Para tentar reduzir a complexidade e minimizar o tamanho do arquivo, vamos
adicionando essas seções uma por vez, a começar pelo `SHT_RELA` (o resto fica
para depois, se precisar).

O primeiro passo seria adicionar um SHT_RELA para fazer o redirecionamento.
Analisando os tipos diferentes de redirecionamento[8], os que mais fazem sentido
são os `R_X86_64_(8|16|32|64)`, e os `R_X86_64_SIZE(32|64)`. Para um primeiro
POC, o objetivo vai ser substituir o primeiro byte por `0xcc` (`int3`). Já que
estamos trabalhando com um byte, vamos usar o tipo `R_X86_64_8`.

  +-Elf64_Ehdr---------------------------+
  |                                      |
  | e_type = ET_DYN                      |
  | e_phnum = 1                          |
  | e_shnum = 2                          |
  |                                      |
  +-Elf64_Phdr[]---------------------[0]-+
  |                                      |
  | p_type = PT_LOAD                     |
  | p_flags = PF_R | PF_X                |
  | p_offset = code_off                  |
  |                                      |
  +-código-------------------------------+
  |                                      |
  | nasm -f bin code.s                   |
  |                                      |
+ +-Elf64_Shdr[]---[0]-+----------------[1]-+
+ |                    |                    |
+ | {0}                | sh_type = SHT_RELA |
+ |                    | sh_link = 0        |
+ |                    | sh_info = 0        |
+ |                    |                    |
+ +-Elf64_Rela[]-------+-------------[0]-+--+
+ |                                      |
+ | r_offset = code_off                  |
+ | r_info = ELF64_R_INFO(0, R_X86_64_8) |
+ | r_addend = 0xcc                      |
+ |                                      |
  +--------------------------------------+

  +-shell-------------------------------------------------------+
  |                                                             |
  | $ readelf -r reloc.out                                      |
  |                                                             |
  | Relocation section 0 at offset 0x12a contains 1 entry:      |
  |   Offset          Info           Type    Sym. Name + Addend |
  | 000000000078  00000000000e R_X86_64_8      cc               |
  |                                                             |
  +-------------------------------------------------------------+
  (cortei a coluna "Sym. Value" do output para caber em 80 caracteres)

O `r_offset` em `Elf64_Rela[0]` indica a posição do endereço virtual do código.
Já que estou utilizando zero como endereço virtual base, os valores de endereço
virtual, físico, e offset vão ser sempre os mesmos.

O output do `readelf -r` parece normal, mas quando roda o programa, o esperado
seria um core dump e uma mensagem sobre trace/breakpoint, mas isso não acontece.
Tem algo faltando.

O trecho da documentação da oracle falando sobre *runtime linker*[10] menciona a
necessidade de um `PT_INTERP` para cuidar de gerar a imagem do programa em
memoria. Esse interpretador pede a presença de um `SHT_DYNAMIC` carregado em
memória através de um segmento `PT_LOAD`.

Ele também fala sobre uma seção `.got`, uma `.plt` (ambas `SHT_PROGBITS`), e uma
`.hash` (`SHT_HASH`). Mas vamos tentar fazer sem elas (sempre tentando remover o
desnecessário). Se o interpretador reclamar, a gente faz.

A seção `SHT_DYNAMIC` aponta para um arranjo de elementos do tipo `Elf64_Dyn`.
Essa struct tem uma tag e um valor. A tag em `d_tag` indica qual o tipo de valor
que vai ter em `d_un`.

  +-Elf64_Dyn----------------------+
  |                                |
  | typedef struct                 |
  | {                              |
  |     Elf64_Sxword d_tag;        |
  |     union                      |
  |         {                      |
  |             Elf64_Xword d_val; |
  |             Elf64_Addr d_ptr;  |
  |         } d_un;                |
  | } Elf64_Dyn;                   |
  |                                |
  +--------------------------------+

A tabela de tags do arranjo *dynamic*[11] indica o que é mandatório ou opcional,
mas eu honestamente nunca fui muito bom em seguir regras, então a gente vai
também ignorar a maioria dos mandatórios. Se reclamar, a gente faz.

Os que parecem mais "mandatórios" para o nosso caso são as tags `DT_RELA`,
`DT_RELASZ`, `DT_RELAENT` e `DT_NULL` (essa ultima tag marca o fim do arranjo).

---[0x03] PROBLEMATIZAÇÃO ------------------------------------------------------

Quando se esta criando o próprio arquivo ELF, não existe muito um problema. Um
único ponto seria talvez o limite de espaço mapeado que o *linker* dinâmico tem
disponível para escrever, mas isso pode ser facilmente circunvido através do
aumento do tamanho que o `PT_LOAD` alvo ocupa em memoria modificando o campo
`p_memsz`.

Sobrescrever as seções também não parece ser um problema, mas os limites dessa
afirmação podem ser testado mais a fundo em um outro momento.

Outro problema é com as relocações do tipo `R_X86_64_(32|64)`. Essas adicionam o
endereço base do símbolo ao calculo (no nosso caso, já que estamos utilizando o
símbolo zero, esse valor seria o endereço base). Essas paginas são alinhadas em
0x1000, então não afetam o primeiro byte e meio, mas todo o resto se torna muito
difícil de determinar. Talvez seja possível utilizar esse ou outro tipo de
relocação caso haja um simbolo especialmente feito para esse motivo, mas vai
ficar para os próximos passos também.

Os maiores pontos problemáticos aparecem ao utilizar essa técnica para a
infecção de arquivos ELF. Devido à natureza do redirecionamento, o segmento
sendo sobrescrito precisa ter permissão de escrita (`PF_W` no respectivo
`p_flags`).

Também é difícil reutilizar os redirecionamentos já existentes no arquivo sem
modificar o funcionamento base do programa, e o número desses são limitados,
fazendo-se difícil infectar um arquivo de maneira trivial com um payload
complexo ou sem que modifique ou quebre completamente o funcionamento original
do programa.

Por último, caso queira adicionar mais redirecionamentos, ou caso queira manter
o funcionamento original do programa, sera preciso, inevitavelmente, criar
mais redirecionamentos, adicionando-os a uma seção já existente, ou criando uma
nova. Esses novos bytes no arquivo vão dar um shift em todos os outros dados em
volta. Será necessário levar em conta todos os offsets sendo mudados, e passar
pelo arquivo inteiro corrigindo esses valores tanto no offset dentro do arquivo
quanto no endereço virtual de qualquer coisa que estiver nas paginas do
mapeamento modificado.

---[0x04] OUTROS TRABALHOS -----------------------------------------------------

Antes de continuar para a conclusão, gostaria de salientar que, mesmo que tenha
descoberto isso tudo sozinho, não fui o primeiro. Antes de fazer todo esse
trabalho, deveria ter pesquisado um pouco mais se alguém já tinha feito algo
parecido.

Consegui encontrar duas menções dessa técnica, ambas a ~5 anos atrás. Ambas
utilizam da relocação para infectar arquivos, mas nenhuma criou um ELF.

A mais velha[13] é uma POC. Ele modifica o `e_entry` para 0, adiciona permissão
de escrita à `PT_LOAD` que cuida do endereço, e busca pelo redirecionamento
referente ao simbolo `__gmon_start__`, modificando o `r_offset` para 0 e
`r_addend` para 0xe9 (a instrução `jmp`) com o objetivo final sendo o de ofuscar
o ponto de entrada.

A segunda menção[14] é um pouco mais complexa. Ela tem uma parte de infecção com
scripts e tudo. Muito legal, recomendo a leitura, mas não vou explicar aqui, se
não fica muito longo.

O mais interessante dessa segunda menção é que a pessoa também implementou um
método de detecção para esse tipo de infecção/ofuscação. Ele olha por relocações
desalinhadas com a memória, intersectadas entre si, ou que estejam utilizando
tipos suspeitos (exatamente os `R_X86_64_SIZE(32|64)` que a gente usa).

---[0x05] CONCLUSÃO ------------------------------------------------------------

Mesmo sendo um pouco difícil a utilização desse método para infecção, suas
peculiaridades com o que se diz respeito à ofuscação trazem alguns benefícios.

O mais proeminente seria suas propriedades Anti-RE. O GDB, assim como vários
outros métodos de depuração e análise dinâmica em Linux, utiliza o `ptrace` para
modificar a memoria de outro programa durante sua execução.

O jeito mais fácil de analisar o código é colocando breakpoints em instruções
interessantes, e analisando o estado do processo naquele dado ponto. GDB alcança
isso salvando a instrução que queremos parar, e substituindo-a pela instrução
`int3` (0xcc) quando essa esta disponível na memoria.

O que o nosso redirecionamento faz é sobrescrever esse `int3`, efetivamente
impossibilitando a ferramenta de pausar a execução do código durante seu
funcionamento. Isso ocorre pois a sobrescrita da relocação ocorre durante a
execução do código, após a sobrescrita do depurador.

Outro beneficio muito aparente é a complicação da análise estática, pois para
quem está analisando, o código é outro. Uma vez que o método é identificado e
compreendido, o analista ainda precisa extrair o código inteiro ou parcial,
juntar com o que está em arquivo, e ai sim continuar sua análise.

Por ultimo, esse método faz uso do interpretador, um programa externo, para
decodificar e escrever o código malicioso em memória. O programa não precisa se
quer mencionar nada sobre algo malicioso, faz uso de ferramentas legitimas para
obter seu resultado.

Mesmo não sendo a primeira pessoa a descobrir essa técnica, ainda me diverti
bastante redescobrindo, mexendo e aprendendo mais sobre o formato de arquivo
ELF, e suas interações com o ambiente Linux. Espero que também tenha gostado e
tirado algum conhecimento daqui.

discord do tramoia.
